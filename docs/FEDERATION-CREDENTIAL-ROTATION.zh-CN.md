# 邻居通信凭证交叠轮换

本阶段实现设计 §18.5、§21.11 的每对邻居通信凭证轮换，保持 `townId`、身份公钥、部署 instance/epoch、访镇授权、租约与消息序列。身份公钥轮换链仍未实现；它需要旧身份签名与新身份挑战的独立协议。

管理员调用 `federation/peerCredentialRotation:start`，参数为 `adminToken`、`peerTownId`、可选 `overlapMs`。交叠默认 15 分钟，允许 10–30 分钟，不接受非整数。`retry` 接受 `adminToken`、`peerTownId`、`rotationId`；`status` 返回经过裁剪的运维状态，可按 `peerTownId` 查询。管理凭据仍来自服务端环境。

请求走 HTTPS `POST /federation/v1/peers/rotate-auth`。双方使用受信身份签名、现有共享密钥 MAC 认证 ECDH P-256 公钥，并通过 HKDF 从 ECDH 结果、旧共享密钥和完整请求/响应派生新密钥。响应同时证明对新密钥的持有。新密钥与 ECDH 私钥只以本地 wrapping key 加密后保存，报文没有密钥明文。响应方提交新密钥并保存原响应；请求方验证响应后提交。丢失响应时重发同一请求并返回原响应，不重新轮换、不延长窗口。

`federationCredentialRotations` 持久保存操作、期限、重试和认证状态。服务端调度重试在重启后继续；管理员也可使用 `retry`。该表属于实时运维状态，不在常规全镇备份、分块备份、选择性导入或迁移归档的数据表清单中，不能通过导入自动恢复邻居信任。加密旧密钥在窗口结束后由 transport maintenance 删除；验证函数在维护执行前也严格拒绝过期旧密钥。

交叠期间当前和上一凭证都能验证请求，ACK 使用该请求实际通过验证的凭证。到期后旧 MAC 一律拒绝。已知已提交轮换的旧发件箱可用当前密钥重新认证原消息，保留原 messageId、nonce、sequence、业务内容和访镇授权；收件箱重复判断只允许 credentialId 变化，对话历史允许其既有 TTL 更新规则。此路径不适用于未完成轮换、撤销或重新配对，也不能跨越部署/身份公钥改变。已认证缓存消息仍受当前信任、原访镇租约与部署 fencing 检查。

撤销信任会删除交叠秘密并撤销轮换重认证记录；重新配对也清理旧记录。暂停时旧凭证不接受，当前凭证的既有清理策略保持不变。一次只允许一个有效轮换，交叠期内不连续轮换。双方同时发起时，按 townId 字典序较小的一方胜出，另一方的待处理轮换被标记 `SUPERSEDED`。

如果请求方直到窗口结束仍未得到响应，状态为 `EXPIRED` 并清除暂存 ECDH 私钥。响应方可能已提交新密钥，此时双方应重新配对恢复连接；不会继续接受过期旧钥，不会更换镇身份。`status` 的错误码和状态用于显示这一情况，不泄露私钥、共享密钥或认证证明。

验证包含双端 HTTP 处理器、保留持久记录的重启模拟和丢失 ACK 重试、篡改请求/响应/新钥证明、交叠期限、并发轮换、重新配对竞争、过期旧钥拒绝与撤销，以及对话历史在交叠到期后保持消息 ID/nonce/序列且不重复入库。
